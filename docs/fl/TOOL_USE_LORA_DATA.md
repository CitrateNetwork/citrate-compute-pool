# Tool-use LoRA data for Gemma 4 E4B (RA-15, HUP-S9.3)

Research note for the first federated LoRA round of the Hermes upskill program. It answers
three questions: which public tool-calling data may go into a Gemma 4 E4B LoRA, how that data
mixes with members' own verified Hermes trajectories, and how the eval set is kept out of
training so the S9.4 eval delta means something.

Planset references: `08_EXTERNAL_RESEARCH.md` section 2 (Hammer, the xLAM cookbook), D-22
(train only on verified turns), D-29 (consent per round), "Eval provenance" in `05`.

## 2. Public tool-calling data

The base model, Gemma 4 E4B, is released under Apache 2.0, so the base adds no use restriction to
an adapter trained on it. The questions are all on the data side.

### 2.1 xLAM function-calling 60k

- Source: `Salesforce/xlam-function-calling-60k` on Hugging Face, produced by the APIGen pipeline.
- Size and shape: 60,000 examples over 3,673 executable APIs in 21 categories. Fields: `query`
  (the request), `tools` (name, description, parameters), `answers` (the expected calls with
  arguments). Single turn: there is no tool result and no final answer.
- Generation: written by DeepSeek-V2-Chat (33,659 entries) and Mixtral-8x22B-Instruct (the
  rest), then filtered by format, execution and semantic checks.
- Licence: CC-BY-4.0. The repository is gated: access requires acknowledging the licence and
  citing APIGen. The card also says the data is released "for research purposes only in support
  of an academic paper".

What that means for us:

1. CC-BY-4.0 allows commercial use and derivatives with attribution, so a LoRA trained on it can
   ship with attribution in its model card.
2. The "research purposes only" sentence on the card sits uneasily with CC-BY-4.0 and with a
   released adapter. It may be advisory, but it is the publisher's stated intent.
3. The text was generated by third-party models. Their output terms (DeepSeek's model licence
   in particular) may add use restrictions that CC-BY-4.0 does not mention.
4. Redistribution: shipping the raw rows to member devices as a public shard is redistribution
   of the dataset. CC-BY-4.0 allows it with attribution, but it bypasses the Hugging Face gate
   the publisher set up.

Conclusion: usable only after the owner (and counsel, if wanted) signs off on points 2 to 4.
Until then the public share of the mix is zero (section 4).

### 2.2 Hammer: function masking and irrelevance data

- Paper: "Hammer: Robust Function-Calling for On-Device Language Models via Function Masking",
  arXiv 2410.04587 (MadeAgents).
- Method: while training, tool and parameter names are replaced with random strings so the
  model has to read the descriptions instead of memorising names. An augmented set teaches the
  model to answer without a tool when none fits.
- Data: `MadeAgents/xlam-irrelevance-7.5k`, CC-BY-4.0, 7,500 rows sampled from xLAM-60k with
  the correct tool removed and the label changed to "irrelevant". It inherits every xLAM
  question above.

What we take from Hammer is the method, which needs no licence: masking applies to public rows
only. Hermes rows keep their real names, because the 29 parity-v1 names are exactly what the
shipping agent calls and the eval scores. Masking them would teach the model to ignore names it
must emit verbatim.

### 2.3 Comparison

| | xLAM-60k | xlam-irrelevance-7.5k (Hammer) | Hermes verified trajectories |
|---|---|---|---|
| Licence | CC-BY-4.0, gated, "research purposes" note | CC-BY-4.0, derived from xLAM | the member's own data, D-29 consent per round |
| Turn shape | single call, no result, no answer | single turn, no call | full turn: call, result, answer |
| Tool surface | 3,673 public APIs | same | the 29 parity-v1 tools |
| Quality filter | APIGen checks | inherited | every workflow verifier passed (D-22) |
| Teaches | argument filling, multiple and parallel calls | when not to call | our tools, our result shapes, how answers cite results |
| Risk | licence questions; style drift toward generic APIs | inherits xLAM's | small and narrow per device; privacy, handled by redaction and consent |

## 3. Trainer input format (`citrate-fl-sft-v1`)

`citrate-fl-dataset` turns an export into one row per verified turn:

```json
{"messages": [{"role": "user", "content": "..."},
              {"role": "assistant", "content": "", "tool_calls": [{"id": "c1", "type": "function",
                "function": {"name": "node_status", "arguments": "{}"}}]},
              {"role": "tool", "content": "...", "tool_call_id": "c1"},
              {"role": "assistant", "content": "..."}],
 "tools": ["memory_search", "...", "calendar_list"],
 "metadata": {"model": "...", "workflow": null, "step": null, "verifiers": ["..."],
              "format": "citrate-fl-sft-v1", "tool_schema": "parity-v1",
              "source": "hermes-verified", "split": "train", "example_id": "<sha256>"}}
```

- `messages` are copied verbatim from the export, so every redaction marker survives. The
  converter does not redact on its own; it trusts nothing it would have to undo.
- `tools` lists the 29 parity-v1 names (citrate-core `src/agent/parity/parity-v1.json`, pinned
  by a hash in both repos). The trainer renders the Gemma tool-declaration block from these
  names and core's tool definitions.
- Dropped and counted: rows that match a held-out item, call a tool outside parity-v1, pass
  arguments that are not a JSON object, have a tool result that answers no call, or repeat an
  earlier row. A line that is not a verified export line (system prompt, no verifier, unknown
  field) is an error: such a file did not come from `export_verified`.
- The rows still pass the device runner's `verify_dataset`, so `CITRATE_FL_DATASET` can point
  at the converted file.

Public rows, when allowed, use the same format with `source: "xlam-60k"` or
`source: "xlam-irrelevance-7.5k"`, their own `tools` list and masked names. They end at the
assistant's call (or, for irrelevance rows, its plain answer), because the sources carry no tool
result. Masking is applied at conversion time with a seed taken from
the round id, so every device masks the same way.

## 4. The mix (recommended default, pending owner sign-off)

Per device, per round:

| Share | Source | Notes |
|---|---|---|
| Hermes rows | the member's converted export, at most `maxTrajectories` (default 500, cap 10,000) | always; the round does not start without at least one row |
| Public tool calls | xLAM-60k, masked | **0 until sign-off**; then up to 2 public rows per Hermes row, at most 1,000 |
| Irrelevance | xlam-irrelevance-7.5k | **0 until sign-off**; then 10 % of the public share |

Why public data at all: one device has a few hundred narrow examples. A small public share is a
regulariser against forgetting general argument filling. Why only up to 2:1: the round's point
is to learn our tools, and the S9.4 gate rejects any adapter where a metric gets worse.

The public shard, once approved, is one file staged like the base model: sha256-named under
`<store>/datasets/`, named in the round config, hash-checked before training, and converted
through the same held-out check.

## 5. The held-out split (toolcall-v2)

- citrate-core's `toolcall-v2` (79 items: v1's 57 plus fragments) is the S9.4 measuring stick.
  Its manifest holds the sha256 of each prompt after normalization (lowercase, everything that
  is neither alphabetic nor numeric becomes a space, whitespace collapsed, trimmed), never the
  prompt text, so prompts do not travel into a training repo.
- The converter drops any example with a user message that normalizes to a held-out prompt.
  The fixture includes one such turn (tc-node-height with different casing and punctuation),
  and the test proves it is removed.
- The manifest is regenerated by core's `heldout.test.ts` and pinned here by sha256. Adding an
  eval fragment in core fails that test until the manifest is regenerated and copied here.
- Limits: matching is exact after normalization. A paraphrase of an eval prompt is not caught.
  injection-v2, workflow-v1 and the QA sets are not in the manifest yet; extending it is a
  follow-up (they are equally "never train" under the eval provenance rule).
- The S9.4 delta compares base and candidate on toolcall-v2 with `eval-tools.mjs --datasets v2
  --adapter-sha256 <sha>`; the gate in core binds the scorecards to the adapter file.

## 6. Decisions for the owner

1. Public data: approve or decline xLAM-60k and xlam-irrelevance-7.5k for a released adapter,
   given section 2.1 points 2 to 4. Recommended default: decline for the first live round
   (Hermes rows only), revisit with counsel before v0.5.0 ships an adapter trained on them.
2. The mix ratios in section 4 (2:1 cap, 1,000 rows, 10 % irrelevance).
3. Extending the held-out manifest to injection-v2, workflow-v1 and the QA sets.
